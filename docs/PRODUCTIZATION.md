## اصل فاز

نرم‌افزار از نظر **ماژول‌ها کامل است**. UI کافی است.
- ❌ بازطراحی رنگ/دکمه/آیکون/چیدمان · ساخت صفحه‌ی CRUD جدید.
- ✅ تبدیل «مجموعه‌ای از ماژول‌ها» به **یک پلتفرم کامل ERP**.

**طرز فکر:** مثل تیم محصول **SAP Business One / Microsoft Dynamics / راهکاران** فکر کن، نه طراح فرم.

### معیار موفقیت
| ❌ نمی‌سنجیم | ✅ می‌سنجیم |
|------------|-----------|
| تعداد صفحه/فرم/دکمه | زمان صرفه‌جویی‌شده |
| | کاهش تعداد کلیک |
| | افزایش اتوماسیون |
| | بهبود بهره‌وری |

### اصل API-First (زیربنای همه‌چیز)
هر عملیات کسب‌وکار = یک **Command/Query در Application** که از طریق **Web API** افشا می‌شود.
کلاینت‌های آینده (دسکتاپ / وب / موبایل) همگی روی همین API سوار می‌شوند. هیچ منطقی در ViewModel نمی‌ماند.

## ۸ حوزه‌ی تمرکز

### ۱) موتور گردش‌کار (Workflow Engine)
برای هر ماژول تعریف می‌شود: **فرایند کسب‌وکار، سفر کاربر، جریان وظیفه، فرصت‌های اتوماسیون، جریان تأیید (Approval)، مدیریت استثناء**.
- زیرساخت: موجودیت `WorkflowState`/`ApprovalRequest` + ماشین وضعیت عمومی (Draft → Submitted → Approved/Rejected → Posted).
- نمونه: فاکتور خرید بالای سقف → نیاز به تأیید مدیر؛ سند پیش‌نویس → تأیید حسابدار ارشد.
- مدیریت استثناء: کسری موجودی، عبور از سقف اعتبار، چک برگشتی → مسیر جایگزین تعریف‌شده.

### ۲) موتور گزارش‌ساز (Reporting Engine)
گزارش‌های فعلی فقط گرید داده‌اند. سیستم گزارش حرفه‌ای:
- زیرساخت `ReportDefinition` (پارامتر، ستون، گروه‌بندی، جمع، فیلتر) + خروجی **PDF/Excel/چاپ**.
- دسته‌ها: **مالی، مدیریتی، انبار، تحلیل فروش، تحلیل شعب، تحلیل مشتری، تحلیل تأمین‌کننده**.
- اجرا سمت Application (Query) تا وب/موبایل هم همان گزارش را بگیرند.

### ۳) داشبوردهای نقش‌محور (Role-Based Dashboards)
هر نقش، داشبورد و KPIهای خودش:
- **مدیر/مالک (Owner/Manager):** فروش/سود/نقدینگی، عملکرد شعب، روند.
- **حسابدار:** اسناد Draft، توازن، دریافتنی/پرداختنی، چک‌های امروز، مغایرت بانکی.
- **انباردار:** کسری موجودی، نقطه‌ی سفارش، رسید/حواله‌ی امروز، انقضا.
- **صندوق‌دار:** شیفت/فروش امروز.
- **رستوران:** میزها/آشپزخانه/گردش.
- پیاده‌سازی: `Get{Role}DashboardQuery` سبک و کش‌شده؛ نقش از `Sec.UserRoles`.

### ۴) هوش تجاری (Business Intelligence)
Queryهای تحلیلی (پارامتر بازه‌ی زمانی، شعبه):
- **مشتریان برتر، کالاهای برتر، تأمین‌کنندگان برتر، عملکرد شعب، تحلیل سود، روند فروش، روند موجودی**.
- خروجی قابل‌مصرف در داشبورد + گزارش + API.

### ۵) اتوماسیون (Automation)
- **اسناد تکراری (Recurring Vouchers)** و **فاکتورهای تکراری** (زمان‌بندی‌شده).
- **پیشنهاد خودکار سفارش خرید** بر اساس نقطه‌ی سفارش/فروش.
- **یادآور خودکار مشتری** (بدهی/سررسید).
- **اعلان سررسید چک** · **اعلان انقضای کالا** · **هشدار کسری موجودی**.
- زیرساخت: جدول `ScheduledJob` + سرویس پس‌زمینه (Hosted Service در API) که Commandها را اجرا می‌کند.

### ۶) بهره‌وری کاربر (User Productivity)
- ادامه‌ی فاز گردش‌کار: کیبوردمحوری، type-ahead، توازن خودکار، اسکن بارکد، میان‌برها.
- الگوها/پیش‌فرض‌های هوشمند، عملیات گروهی (bulk)، ورود سریع.

### ۷) پلتفرم API (API Platform)
- **هر Command/Query یک endpoint** در `SamaHesab.API` داشته باشد (نه فقط آن‌هایی که کلاینت لمسی لازم دارد).
- استانداردسازی: احراز JWT + نقش، نسخه‌بندی (`/api/v1`)، پاسخ یکنواخت `Result<T>`، صفحه‌بندی، مستند **OpenAPI/Swagger**.
- ممیزی: هر تغییر داده از طریق API لاگ شود.

### ۸) آمادگی وب (Web Readiness)
- چون منطق در Application است، کلاینت وب (Blazor/React) فقط API مصرف می‌کند.
- پیش‌نیاز: تکمیل پوشش API (#۷) + CORS + احراز توکن + قراردادهای DTO پایدار.

### وضعیت پایه‌ی موجود (که روی آن می‌سازیم)
- معماری CQRS/MediatR + Web API + JWT از قبل هست (کلاینت‌های POS/رستوران/انبار روی API کار می‌کنند).
- داشبورد فعلی همه‌ی KPIها را یک‌جا دارد → ورودی خوب برای تفکیک نقش‌محور.
- بک‌اند آماده‌ی فاز قبل: توازن سند، تخصیص FIFO دریافتنی/پرداختنی، تابلوی چک، مغایرت‌گیری بانکی.
