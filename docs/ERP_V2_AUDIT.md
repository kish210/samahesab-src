# سما حساب — ممیزی محصول و نقشه‌ی راه نسخه‌ی ۲
### ERP Product Audit & v2 Roadmap

> هدف: تبدیل «سما حساب» از مجموعه‌ای از فرم‌ها به یک **محصول ERP تجاری** قابل فروش در بازار ایران،
> قابل‌قیاس با Sepidar / Holoo / Rahkaran و با معماری آماده برای Desktop + Web + Mobile.
> این سند بر پایه‌ی وضعیت واقعی کد (نه فرض) نوشته شده. آخرین به‌روزرسانی: 2026-06-09.

---

## ۰. حکم کلی (Executive Verdict)

| محور | وضعیت فعلی | فاصله تا محصول تجاری |
|---|---|---|
| معماری (Clean/CQRS/API) | استخوان‌بندی درست، اجرای ناقص | متوسط — اصلاح‌پذیر |
| عمق منطق کسب‌وکار | فقط ۱۴ هندلر CQRS؛ بقیه CRUD | **زیاد** |
| حسابداری | ثبت/تأیید سند پایه | متوسط |
| انبار | موجودیت‌ها هست، فرایندها نیست | **زیاد** |
| فروشگاه (POS) | فروش سریع پایه | متوسط |
| رستوران | **مدل دامنه وجود ندارد** | **بحرانی** |
| چندشعبه | `CompanyId` دارد، `BranchId` ندارد | **زیاد** |
| نقش‌محوری تجربه‌ی کاربری | تک‌پوسته برای همه | **زیاد** |
| کیفیت (تست/CI) | بدون تست | **زیاد** |
| آماده‌ی وب/موبایل | API هست، منطق در WPF نشت کرده | متوسط |

**نتیجه:** پایه‌ی فنی ارزشمند است؛ مشکل اصلی این است که **منطق کسب‌وکار در ViewModelها زندانی شده** و **فرایندهای عملیاتی واقعی پیاده نشده‌اند**. نسخه‌ی ۲ باید «منطق را به Application ببرد» و «فرایندها را بسازد»، نه اینکه فرم‌های زیباتر بسازد.

## ۱. ممیزی معماری

### نقاط قوت (نگه‌داشتنی)
- لایه‌بندی Domain / Application / Infrastructure / API / WPF.
- API (`SamaHesab.API`) همان `AddApplication()` + `AddInfrastructure()` دسکتاپ را مصرف می‌کند → کلاینت‌های فروشگاه/رستوران از طریق API کار می‌کنند (تأییدشده).
- موجودیت‌های دامنه‌ی غنی برای انبار (Batch/Serial/StockTransaction با فیلدهای بهای تمام‌شده).

### بدهی‌های معماری (باید در v2 رفع شود)
1. **نشت منطق به UI:** فقط ۱۴ هندلر؛ اکثر صفحات مستقیم با Repository/DbContext کار می‌کنند.
   → قانون v2: **هر عملیات کسب‌وکار = یک Command/Query در Application.** ViewModel و Controller فقط `IMediator.Send` می‌کنند. این تضمین «۸۰٪ استفاده‌ی مجدد در وب» است.
2. **Domain Events مرده:** `BaseEntity.AddDomainEvent` هست ولی هیچ‌جا رخداد منتشر نمی‌شود.
   → v2: رخدادها (SaleCompleted, StockReceived, VoucherPosted) را منتشر و با هندلر مصرف کن (سند خودکار، کاردکس، اعلان).
3. **چندشعبه‌ی ناقص:** `AuditableEntity` فقط `CompanyId` دارد.
   → v2: افزودن `BranchId` به `AuditableEntity` + فیلتر سراسری EF (Global Query Filter) بر اساس شرکت/شعبه + کلِیم `branchId` در JWT (که الان هم صادر می‌شود) → فیلتر داده per-branch.
4. **بدون تست/CI:** هیچ پروژه‌ی تستی نیست.
   → v2: پروژه‌ی `SamaHesab.Tests` (xUnit) برای منطق حسابداری (تراز سند)، بهای تمام‌شده‌ی انبار، و قیمت‌گذاری فروش.
5. **یکپارچگی تراکنشی:** ثبت فروش باید اتمیک باشد (فاکتور + کاهش موجودی + سند حسابداری + دریافت).
   → v2: یک Unit-of-Work/Transaction در هر Command؛ رخداد دامنه برای اثرات جانبی.

## ۲. ممیزی ماژول‌ها (وضعیت → ضعف → هدف فرایندی)

### ۲.۱ حسابداری (قلب سیستم)
- **هست:** `CreateVoucher`, `PostVoucher`, `GetVouchers`, گزارش‌های مالی پایه، نمودار حساب‌ها، چک، بانک.
- **ضعف:** بدون دفتر معین/تفصیل تعاملی، بدون تراز آزمایشی چندسطحی زنده، بدون بستن سال مالی، بدون سند افتتاحیه/اختتامیه، بدون سند خودکار از فروش/انبار (یا تأییدنشده)، بدون اسناد تکراری/الگو.
- **بنچ‌مارک (Sepidar/Rahkaran):** ورود سند کیبردمحور با کد تفصیلی شناور، تراز چندستونه، دریل‌داون از تراز → معین → سند.
- **هدف v2:**
  - موتور سند خودکار رویدادی: هر فاکتور فروش/خرید/دریافت/پرداخت → سند تأییدشده.
  - کوئری‌های GL: تراز آزمایشی (۲/۴/۶/۸ ستونی)، دفتر معین، دفتر تفصیلی، با دریل‌داون.
  - ورود سند سریع: tab/enter محور، تکرار ردیف، الصاق پیوست، توازن آنی بدهکار/بستانکار.
  - بستن دوره و سال مالی، سند افتتاحیه خودکار.

### ۲.۲ انبار
- **هست:** موجودیت‌های Product/Warehouse/StockItem/StockTransaction/Batch/Serial/ProductPriceLevel؛ فقط `TransferStock` + `GetKardex`.
- **ضعف:** بدون فرایند **رسید ورود**، **حواله‌ی خروج**، **انبارگردانی (Stock Count)**، **تعدیل**، بدون موتور **بهای تمام‌شده (FIFO/میانگین موزون)** با اینکه فیلدهایش هست، بدون کنترل **انقضا** و **سریال** در جریان کار.
- **بنچ‌مارک:** فرایند سندمحور انبار (رسید/حواله با تأیید)، انبارگردانی با شمارش و مغایرت‌گیری، بارکدخوان پیوسته.
- **هدف v2:**
  - Commandها: `ReceiveStock`, `IssueStock`, `AdjustStock`, `StartStockCount`/`PostStockCount`.
  - موتور costing واقعی (FIFO و میانگین موزون) که `UnitCost/BalanceCost` را پر کند و به سود فروش وصل شود.
  - جریان بارکد پیوسته (اسکن → ردیف)، کنترل انقضا/بچ در رسید و فروش، ردیابی سریال.

### ۲.۳ فروشگاه (POS)
- **هست:** `PosViewModel` با فروش از طریق API، بارکد، چند روش پرداخت، چاپ رسید.
- **ضعف:** بدون **شیفت/صندوق (Session)**، بدون **گزارش X/Z**، بدون مغایرت کشو، بدون **مرجوعی**، بدون hold/recall فاکتور، بدون مشتری سریع/باشگاه.
- **بنچ‌مارک:** فروش زیر ۱۰ ثانیه، باز/بستن شیفت، شمارش صندوق، مرجوعی با رسید.
- **هدف v2:** Session صندوق (باز/بست + شمارش)، گزارش Z، مرجوعی، تعلیق/فراخوان فاکتور، میان‌برهای کیبرد کامل.

### ۲.۴ رستوران (بحرانی‌ترین فاصله)
- **هست:** فقط `RestaurantPosView` به‌عنوان پوسته‌ی POS. **هیچ موجودیت دامنه‌ای نیست.**
- **ضعف:** بدون **میز/سالن**، بدون **سفارش باز روی میز**, بدون **آشپزخانه (KDS)**، بدون وضعیت غذا، بدون بیرون‌بر/پیک/رزرو، بدون تخصیص گارسون.
- **بنچ‌مارک:** میز→سفارش باز→ارسال به آشپزخانه→وضعیت→تسویه؛ نمایشگر آشپزخانه (KDS).
- **هدف v2 (مدل دامنه‌ی جدید):**
  - موجودیت‌ها: `Hall`, `DiningTable`, `RestaurantOrder`, `OrderItem(+Status)`, `KitchenTicket`, `Reservation`, `WaiterAssignment`.
  - فرایندها: باز کردن میز، افزودن آیتم، **ارسال به آشپزخانه**، تغییر وضعیت (در حال آماده‌سازی/آماده/سرو شد)، انتقال/ادغام میز، تسویه و انعام.
  - نمایشگر آشپزخانه (KDS) به‌صورت کلاینت جداگانه روی همان API.

### ۲.۵ CRM
- **هست:** مشتری/تأمین‌کننده + `GetCustomerStatement`.
- **ضعف:** بدون **اعتبار/سقف اعتبار**، بدون یادآوری/پیگیری، بدون تاریخچه‌ی خرید تحلیلی، بدون باشگاه مشتریان/امتیاز.
- **هدف v2:** سقف اعتبار و کنترل آن در فروش، تاریخچه و تحلیل مشتری، یادآور بدهی/چک، پیامک رویدادی.

### ۲.۶ منابع انسانی / تنظیمات / گزارش
- HRM پایه (پرسنل/حضور/حقوق) — اولویت پایین برای تجاری‌سازی خرده‌فروشی.
- گزارش: نیاز به یک **موتور گزارش پارامتریک** (فیلتر/گروه‌بندی/خروجی Excel/PDF) به‌جای صفحات جدا.

## ۳. استراتژی تجربه‌ی نقش‌محور (Role-based Workspaces)

به‌جای یک پوسته برای همه، **حالت اجرا بر اساس نقش** (مدل فعلی `--pos`/`--restaurant` را گسترش بده):

| نقش | فضای کاری بهینه |
|---|---|
| صندوق‌دار فروشگاه | تمام‌صفحه، لمسی+کیبرد، فروش زیر ۱۰ ثانیه، شیفت |
| گارسون رستوران | لمسی، انتخاب میز/سالن، ارسال به آشپزخانه |
| آشپزخانه | KDS فقط‌خواندنی، صف سفارش، تغییر وضعیت |
| صندوق رستوران | تسویه‌ی میز، انعام، گزارش شیفت |
| حسابدار | گریدمحور، چگال، کیبردمحور، ورود سریع سند |
| انباردار | فرایندمحور، رسید/حواله/انبارگردانی، بارکد |
| مدیر فروشگاه/شعبه | داشبورد عملیاتی + گزارش‌های شعبه |
| مالک | داشبورد مدیریتی چندشعبه، KPI |
| مدیر سیستم | کاربران/دسترسی/تنظیمات/پشتیبان |

اصل: Ribbon با Auto-Collapse + Contextual Tabs؛ ناوبری ۶۰px/۲۲۰px با حفظ ترجیح کاربر و **مخفی‌شدن خودکار در حالت عملیاتی**. Telerik فقط جایی که بهره‌وری را بالا می‌برد (RadGridView/RadDataFilter برای حسابداری و انبار؛ RadDocking برای میزکار حسابدار؛ کارت/تایل لمسی برای POS/رستوران).

## ۴. نقشه‌ی راه فازبندی‌شده‌ی v2

ترتیب بر اساس **بیشترین ارزش تجاری ÷ ریسک**:

- **فاز ۰ — پایه‌ی معماری (پیش‌نیاز همه):**
  افزودن `BranchId` + Global Query Filter؛ فعال‌سازی Domain Events؛ پروژه‌ی `SamaHesab.Tests`؛ قانون «هر عملیات = یک Command».
- **فاز ۱ — رستوران واقعی (بزرگ‌ترین شکاف بازار):**
  مدل دامنه‌ی میز/سالن/سفارش/آشپزخانه + فرایندها + KDS. این تمایز فروش است.
- **فاز ۲ — انبار فرایندمحور + بهای تمام‌شده:**
  رسید/حواله/انبارگردانی/تعدیل + موتور FIFO/میانگین موزون متصل به سود فروش.
- **فاز ۳ — حسابداری حرفه‌ای:**
  سند خودکار رویدادی، تراز/معین/تفصیل با دریل‌داون، بستن دوره/سال.
- **فاز ۴ — POS تجاری:**
  شیفت/صندوق، Z-report، مرجوعی، تعلیق/فراخوان.
- **فاز ۵ — CRM + اعتبار + باشگاه مشتریان.**
- **فاز ۶ — کلاینت وب (Blazor/React روی همان API) و موبایل.**

## ۵. اولین قدم پیشنهادی (Phase 0 + شروع Phase 1)

1. `BranchId` در `AuditableEntity` + Query Filter + سیدِ شعبه‌ی پیش‌فرض.
2. روشن‌کردن Domain Events با یک نمونه‌ی واقعی: `SalesInvoicePosted → سند حسابداری خودکار`.
3. ساخت پروژه‌ی تست و نوشتن تست‌های توازن سند و costing.
4. شروع مدل دامنه‌ی رستوران (`Hall`, `DiningTable`, `RestaurantOrder`, `OrderItem`, `KitchenTicket`).

> هر فاز با Commۤand/Query در Application شروع می‌شود (قابل‌استفاده در WPF و وب)، سپس UI نقش‌محور.
